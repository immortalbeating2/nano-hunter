# Stage26 后北极星差距评估与 Stage27-32 路线设计

## 文档定位

> 2026-08-29 取代说明：本文中的 `44` 房 Stage31 候选、Gate26H 与 Stage32 依赖链属于历史路线。F01–F18 Blueprint V2 已改变正式路线，后续还将重设整体关卡；旧 Gate26H 已以 `SUPERSEDED / NOT EXECUTED` 关闭，不再作为合并或 Stage32 的命名硬门禁。真人路线、手柄、存档、21:9、美术与音频验收没有被豁免，将在新关卡设计冻结后由新候选门禁承接。本文保留为历史设计记录。

本文以 `spec-design/2026-03-23-nano-hunter-design.md` 为北极星，以 2026-07-31 当前代码、Stage26 交付审计、本次 Stage21-26 组合回归、Godot MCP Pro 运行态与资产审计为事实基线，回答两个问题：

1. 当前 Alpha Candidate 距离玩家可感知的北极星体验还有什么差距。
2. 下一批正式 Stage 应按什么顺序开发、每个 Stage 到哪里停止。

本文取代“Stage20 后规划 Stage21-26”的路线决策，但不改写 Stage21-26 已完成的历史范围。Stage21-26 的批准范围已经实现并完成自动与代理运行态收口；剩余真人首次通关、能力回访、悬赏 / Build 理解度和手柄主观舒适度仍是开放的外部签核。该真人门禁不再阻塞 Stage27-31 开发，但在 Stage32 Beta Candidate 对外签核前必须完成，不得改写为已经通过。

## 总结判断

当前项目已经形成北极星 Alpha 的系统骨架：两元素、两姿态、两步序列能驱动敌人反应、悬赏、Build 和雷泽机关，44 房世界图也具备回访闭环。它尚未达到北极星 Beta 垂直切片，更不等于完整商业版。

真正的下一缺口不是继续堆元素或房间，而是把现有系统转成玩家无需读调试文字也能理解的体验：

- 元素、姿态和两种序列仍共用同一攻击动作与同一组 VFX，只靠颜色、判定和 HUD 文字区分。
- 镇妖驿站仍主要是背景复用、触发点和详情面板，缺少正式悬赏榜、NPC 和镇妖卫叙事锚点。
- 四件 Build 有数值差异，但缺少独立图标、槽位构图和获得反馈。
- 雷泽荒原六房的玩法结构成立，但视觉仍是瘴泽背景染蓝、Polygon 雷纹 / 祭柱 / 屏障和既有门图的灰盒组合。
- 角色、敌人和 Boss 的既有动作资源可运行，但只达到技术可用：Luna 当前代码实际引用 `7` 个动作片段、`111` 帧与两套各 `8` 帧攻击 VFX；Seal Guardian 实际引用 `5` 个动作片段、`24` 帧与一套 `8` 帧攻击 VFX。Stage21-25 没有为元素、姿态、序列或雷泽内容新增专属动作帧。
- `assets/audio/` 只有目录占位，攻击、敌人预警、UI、区域氛围和 BGM 均未接入。
- 当前资产生产队列已扩为 `56` 项，但 runtime integration map 与旧 final-ready 门仍只有 `55` 项；已在生产 UI 引用的 `stage19_discovery_map_base_ai01` 尚未登记，严格 runtime-map 审计失败。
- 世界观只通过少量文本出现，Luna 的镇妖卫身份、佛妖混血、官僚腐化和人与妖的偏见尚未形成连续可玩叙事。
- 仍无跨进程存档；Continue 不是正式继续游戏，驿站也没有快速旅行功能。

因此，当前可以称为“北极星系统 Alpha 已形成”，不能称为“北极星内容、美术或发布体验已完成”。

## Stage 开发前自动门禁：Preflight26A

Preflight26A 不扩玩法，只把 Stage27 的起点恢复为可重放、可审计基线：

1. 明确当前地形视觉 / 碰撞改动的提交与分支归属，不把未提交现场混入 Stage27。
2. 将已在 `DemoShell` 运行引用的 `stage19_discovery_map_base_ai01` 补入 runtime integration map、readiness 与 acceptance 边界，重新执行全部 strict 资产审计。
3. 从确认后的基线重跑 Stage21-26 组合、Godot import、主场景 smoke 与 `git diff --check`。
4. 确认 Godot MCP 临时 autoload 为零；本次审计新鲜基线为 Stage21-26 `31/31` tests、`294` assertions，Godot `4.6.3` 主场景启动与编辑器错误 `0`。

## 可自动执行的技术门禁：Gate26M

Gate26M 使用 Godot MCP Pro、GUT 与生产场景完成确定性技术复核，可在 Stage27 前执行，并在 Stage27-31 每阶段重复：

1. 确认 bridge workspace 与当前项目根目录完全一致，读取项目版本、输入动作和编辑器错误。
2. 启动生产主场景，模拟主菜单、暂停、地图、详情、元素 / 姿态切换、攻击与返回链路；断言焦点、暂停状态、HUD 和关键进度字段。
3. 用连续帧、截图和输出日志检查动作是否实际切换、VFX 是否按预期出现、场景是否报错。
4. 用 GUT 固化可重复的输入、状态、存档和回归断言。

Godot MCP Pro 可以证明“输入到达、状态正确、画面变化、流程可走”，不能证明按键舒服、是否误解规则、是否迷路、动作是否具有审美完成度。因此 Gate26M 不能代替 Gate26H。

## 延后真人门禁：Gate26H

Gate26H 不再作为 Stage27 开发前置，可延后到 Stage31 完成后，与 Stage32 Beta Candidate 真人验收合并执行。延后期间 Stage26 保持“待外部人工签核”，Stage27-31 只能声称自动 / MCP 技术门禁通过，不能声称真人体验通过。

最终至少完成一次 `30-45` 分钟真人基线：

1. 从主菜单开始完成一次首次通关。
2. 完成一次能力回访、一次悬赏回交和一次两槽 Build 调整。
3. 使用实体手柄记录元素 / 姿态切换、菜单误按、按键舒适度和路线迷失点。
4. 复核 Luna 全动作集、四类攻击 VFX、Seal Guardian 与雷泽首领的读招和命中反馈。

## Stage27：正式战斗美术、Luna 全动作集与首批音频

### 目标

先把主角和既有 Boss 提升到正式 Demo 的战斗展示标准，让玩家不依赖右上角文字，也能从动作、颜色、形状和声音分辨风、雷、疾印、御印及两种序列结果。

### 范围

- 保留现有两元素、两姿态、两步序列和 `receive_elemental_attack(...)` 契约，不新增第三元素或第二套伤害框架。
- 为风击、雷击、风→雷、雷→风提供四种轮廓和节奏不同的运行 VFX；不能只给同一 VFX 换色。
- 将 Luna 当前所有生产动作统一清稿并补齐正式全动作集：idle、run、jump start / rise / apex / fall / land、air dash、疾印地面攻击、御印地面攻击、空中攻击、两种序列收势、元素切换、姿态切换、恢复、hit、death。现有 `7` 个片段只能作为候选底稿，逐项通过一致性与运行态门禁后才能保留。
- 现有 Seal Guardian 同步完成正式 Demo 级动画 / VFX polish：idle、两种 warning / attack、guard break / stagger、phase transition、defeat，以及 warning、impact、破印、转阶段和消散特效；不以当前 `5` 个短片段和单套攻击 VFX 直接签核。
- 接入首批 P0 音频：攻击 / 命中、元素 / 姿态切换、两种序列、受伤、敌人预警、Boss 破印、UI 焦点 / 确认 / 返回。候选通过 `local-game-audio` 路由生成：SFX 使用 Stable Audio 3 Small SFX，BGM / stinger 使用 ACE-Step 1.5；先进入本机 scratch，试听接受和来源记录后才复制到项目运行目录。
- 复用当前 Stage26 调试选关，增加仅开发环境可见的“北极星全能力预设”：授予 Air Dash、风印、四件 Build 和 Stage21-25 所需状态；不得进入发布菜单或改正式存档。
- 允许小范围命中停顿、镜头震动或色闪调参，但必须有关闭入口并保持碰撞 / 伤害权威不变。

### 美术 / 动画包

- `NS27-LunaFormalMotion`：Luna 正式全动作集，目标包络约 `18` 个片段、`150-200` 个最终可用独立帧；该数量是排产包络，不是以帧数代替质量验收。
- `NS27-CoreCombatVFX`：风、雷、风→雷、雷→风四类技能 VFX，以及姿态 / 元素切换、命中、恢复和 Air Dash 反馈。
- `NS27-SealGuardianPolish`：既有 Seal Guardian 高质量动作、阶段反馈和 Boss 特效包。
- `NS27-Audio` 首批战斗与 UI 音频包。

### 退出标准

- 玩家在关闭序列文字提示的测试条件下能稳定区分两元素和两种顺序结果。
- Luna 全动作在生产场景内无明显根部漂移、体积跳变、抠图色边和动作语义混用；地面 / 空中攻击、两姿态和两种序列均有可辨轮廓。
- Seal Guardian 两阶段、预警、命中、破印、硬直与击败无需读状态文字即可辨识。
- 全能力预设能在一个会话内复核全部玩家能力，且发布模式不可见。
- 音频事件无重复叠爆、无明显延迟，音量可从设置入口控制。
- Stage21 / 22 / 24 / 26 专项、邻近战斗、全量回归、import 与 Gate26M 运行态通过；真人主观签核允许延后到 Gate26H。

### 非目标

- 不新增第三元素、技能树、法力、异常状态表或新房间。
- 不建立通用骨骼动画框架，不让 SpriteFrames 反向控制碰撞、伤害或状态机。

## Stage28：镇妖驿站叙事锚点与悬赏 / Build 表现

### 目标

让 Stage11 第一次真正读成镇妖卫驿站，并用最短剧情链建立 Luna 的公开身份与官僚腐化线索。

### 范围

- 保留三条固定悬赏和四件 Build 的数据边界，替换世界内复用 marker 与纯文字列表。
- 接入正式驿站背景 / 地形、三状态悬赏榜 prop、驿卒 NPC 和一张半身像。
- 使用现有 DetailPanel 交付三段短事件：首次到站、三榜回交、雷泽归来；不引入通用对话插件或分支编辑器。
- 为三条悬赏、四件 Build 和两个槽位提供独立图标 / 选中态 / 装备态，并完成手柄焦点与 32px / 64px 读值复核。
- 把“镇妖卫公开身份、郡守私运妖骨、妖声共鸣”串成一条可理解的最小叙事链。
- 接入榜单、奖励、装备、NPC 和驿站环境音效。

### 退出标准

- 首次玩家无需口头说明即可完成接榜、回交和更换两槽 Build。
- 驿站、悬赏榜和四件物品在世界与 UI 中均有唯一视觉身份。
- 三段事件可回归、可跳过、不会因暂停 / 切房重复触发。

### 非目标

- 不做随机悬赏、货币、交易市集、NPC 群像、对话树或完整物品栏。

## Stage29：雷泽荒原正式美术与区域机制清稿

### 目标

保留 Stage25 已验证的六房拓扑，把“瘴泽背景染蓝 + Polygon 机关”的灰盒升级为可被一眼识别的雷泽区域。

### 范围

- 不增加房间数量；重做现有六房的区域构图、地形边缘、背景和地标。
- 接入雷泽专用 `TileSet`、安全 / 危险地表、2-3 层可延展背景、风蚀碑、引雷柱、雷云与荒原植被 / 残旗 prop。
- 把雷暴、接地祭柱、屏障和出口箭头的 Polygon 表现替换为正式状态资产和 VFX，逻辑继续复用 Stage25 节点。
- 将入口 checkpoint 表现为“雷泽前哨”，作为 Stage31 第二传送点的场景准备，但本阶段不实现传送。
- 接入雷泽环境氛围与一条探索 BGM；复核 16:9、2K 和 21:9 安全边界。

### 退出标准

- 六房不再引用瘴泽背景作为雷泽主背景，不再以大块纯色 Polygon 承担关键机关完成表现。
- 安全地表、危险区、可交互祭柱和出口在无 HUD 条件下可区分。
- 现有路线、碰撞、接地逻辑和世界图不因美术替换改变。

### 非目标

- 不扩房、不加第三元素、不在本阶段加入区域 Boss。

## Stage30：雷泽敌群、区域首领与元素吸收成长

### 目标

让雷泽从“机关房集合”变成有生态、首领和成长回报的区域，同时证明 Luna 的妖性吸收能改变战斗与回访。

### 范围

- 新增一个雷泽普通敌人家族和一个两阶段区域首领；优先复用 BaseEnemy、`receive_attack(...)`、`defeated` 和现有 Boss 状态边界。
- 两种现有序列都必须对敌人或首领产生不同且可读的优势，普通攻击仍可完成战斗。
- 首领击败后授予一个雷系吸收强化和一个大妖组件；强化至少改变一个战斗读值和一个既有回访门控，具体数值在 Stage30 专属设计中锁定。
- 新增一段妖性共鸣事件，把战斗奖励与 Luna 身份连接起来。
- 为新敌人、首领、Boss 房、吸收反馈、组件和战斗音频制作专属资产。雷泽首领按正式 Demo Boss 标准制作独立 warning、两阶段攻击、phase transition、guard break / stagger、hit、defeat 与配套 warning / impact / phase / defeat VFX，不以 Seal Guardian 换色或短循环代替。

### 退出标准

- 普通敌人、首领两阶段、两序列反应、击败奖励和一处回访收益形成完整闭环。
- 新动画覆盖敌人 idle / move / attack / hit / defeat 与首领 idle / warning / 两阶段 attack / stagger / defeat，运行时锚点和动作窗口通过审计。
- 不因新增内容建立第二套敌人生命、伤害或通用状态框架。

### 非目标

- 不新增第三元素，不实现完整 6-8 元素池，不建立通用 Boss 编辑器。

## Stage31：单档存档与双驿站传送

### 目标

让 Continue 成为真实功能，并降低驿站、雷泽和回访路线之间的重复跑图成本。

### 范围

- 使用一个带版本号的本地存档，持久化 checkpoint、地图发现、能力、悬赏、Build、Boss / 区域关键状态；继续复用 Main 快照，不平行建立第二套进度模型。
- 写入失败时保留上一个有效档；损坏档明确提示并允许安全新开。
- 主菜单 Continue 只在有效存档存在时可用。
- 只在 Stage11 镇妖驿站与 Stage29 雷泽前哨之间提供两点传送，且必须先发现目标点。
- 接入存档、传送、checkpoint 状态图标与必要音效。

### 退出标准

- 关闭程序后可从正确 checkpoint 恢复，悬赏 / Build / 地图 / Boss 状态与存档前一致。
- 损坏档不会导致启动崩溃或覆盖最后一个有效档。
- 双点传送不绕过未解锁门控，不扩成任意房间传送。

### 非目标

- 不做多存档槽、云同步、跨平台同步、复杂迁移框架或全地图传送网。

## Stage32：北极星 Beta Candidate 收口

### 目标

冻结新内容，把 Stage27-31 收成可由外部玩家完整复核的北极星 Beta 候选。

### 范围

- 不新增元素、敌人、房间、悬赏或 Build，只修连续试玩暴露的问题。
- 完成音量、UI 缩放、震动 / 屏幕震动等已存在反馈的必要设置；输入重绑定是否进入本阶段由 Stage27-31 实际输入债务决定。
- 完成 Windows 导出、性能、存档、手柄、暂停 / 地图 / UI、失败恢复和宽屏矩阵。
- 完成正式标题字、菜单细节、运行时美术总检、资产来源 / 发布授权复核和音频混音。
- 执行至少一次陌生玩家首次通关，以及悬赏 / Build / 雷泽 / Boss / 存档 / 传送的定向复核。

### 退出标准

- 自动化、import、主场景 smoke、Windows export smoke 和递归回归通过。
- 外部玩家能在无开发者提示下完成核心闭环，P0 / P1 体验问题清零。
- 正式运行资源、标题字、音频与发布候选的来源和授权边界有记录。
- 发布说明明确区分 Beta 垂直切片与完整商业版剩余内容。

## Stage 顺序与依赖

```text
Preflight26A
  -> Gate26M 自动 / MCP 技术基线
  -> Stage27 Luna 全动作 / 核心 VFX / 既有 Boss / 音频
  -> Stage28 驿站 / 叙事 / 悬赏与 Build 表现
  -> Stage29 雷泽正式美术
  -> Stage30 雷泽敌群 / 首领 / 吸收成长
  -> Stage31 单档存档 / 双驿站传送
  -> Gate26H 延后真人签核
  -> Stage32 Beta Candidate
```

- Stage27 先把项目独特战斗变成可感知语言，否则新增内容只会放大灰盒反馈。
- Stage28 先建立任务与成长锚点，Stage29-30 才有清晰的出发、回交和叙事落点。
- Stage29 先完成区域视觉与场景契约，避免 Stage30 敌人 / Boss 在灰盒区域上反复返工构图。
- Stage31 等进度字段稳定后再持久化，避免为仍在变化的数据提前设计迁移。
- Stage32 只收口，不接新内容。
